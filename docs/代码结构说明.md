## 2. 模块分层与依赖

整个仓库严格分层，**没有循环依赖**，任何模块都能单独 `import`。

| 层 | 模块 | 职责 |
|---|---|---|
| L0 基础设施 | `hfsp_environment.py` | 问题建模、解码器、NEH/SPT |
| L0 基础设施 | `schedule_distance.py` | 商集签名与结构距离 |
| L1 基础算子 | `iterated_greedy.py` | IG 破坏-重建-退火接受 |
| L1 基础算子 | `niching_mechanism.py` | 小生境分组、种群多样性、位置距离（旧） |
| L2 搜索器 | `niching_pso.py` | 离散 PSO 主循环 |
| L2 搜索器 | `archive_guided_search.py` | 档案库引导搜索 |
| L3 编排 | `multimodal_hfsp_solver.py` | 配置、档案库、三种求解模式、结果组装 |
| L4 入口 | `run_*.py` `demo_*.py` `report_*.py` | 命令行脚本 |
| 旁路 | `multimodal_evaluation.py` | 多模态评价指标 |
| 旁路 | `solver_analysis.py` | 瓶颈/利用率/等待时间分析 |
| 旁路 | `gantt_chart_generator.py` | 甘特图导出 |

依赖方向（箭头 = 被导入）：

```
hfsp_environment ──> niching_mechanism ──> niching_pso ─────────┐
        │                                                        │
        ├──> schedule_distance ──> archive_guided_search ────────┼──> multimodal_hfsp_solver
        │                                                        │            │
        └──> iterated_greedy ────────────────────────────────────┘            │
                                                                             ▼
                                          solver_analysis / multimodal_evaluation / gantt_chart_generator 
```

**设计原则**：解码器（`hfsp_environment`）是所有算法的唯一「评价入口」，PSO 和 IG 都不自己算 makespan，只调用 `env.decode_and_evaluate(π)`。这样评价口径只有一处定义，改了解码器不会漏改。

## 3. 一次完整求解的数据流

以 `solve_environment(env, config, mode="basic_pso_ig")` 为例，时间线上发生的事：

```
① env.neh_heuristic()      → NEH 解（按平均加工时间降序 + 最优插入）  ← 算 baseline
② env.spt_heuristic()      → SPT 解                                  ← 算 baseline
③ _run_basic_pso_ig():
   3.1  NichingPSO.run()   → 种群迭代 60 代
          · 每代每个粒子：速度更新 → 位置更新 → 变异 → 评价
          · 每次评价顺便写进「候选解缓冲池」(_record_solution)
          · 停滞时用档案库排列池注入精英重启
          · 每 12 代对 gbest 跑一次 IG 精修
   3.2  ig.optimize(gbest) → PSO 结束后再补一轮 IG（两阶段范式）
   3.3  ig.find_multimodal_solutions() → 扰动 + IG，采 5 条候选
   3.4  _build_archive()   → 候选解经过入档四步，得到档案库
   3.5  档案库引导（config.archive_guided_rounds > 0 时）
          · 可选：用档案库排列池重启 PSO（archive_pso_restart_generations）
          · ArchiveGuidedSearch.run()：种子选择 → 多样化游走 → 回写
   3.6  取档案库首名作为最终最优解
④ _build_solver_result()   → 组装 best_solution / archive / analytics / metadata
```

关键点：**档案库不是最后才建的**。`3.4` 建出来之后，`3.5` 会把它当成搜索的状态变量继续用，`3.6` 还可能因为档案库里的解更好而更新最终结果。

## 4. 逐模块详解

### 4.1 `hfsp_environment.py`（256 行）— 问题建模与解码

**职责**：把 HFSP 算例变成可计算对象，并定义唯一的「排列 → 调度」解码规则。

**数据结构**（全部是 frozen dataclass，可安全缓存与比较）：

```python
@dataclass(frozen=True)
class Operation:            # 一道工序
    job_id: int
    stage_id: int
    machine_id: int
    start_time: int
    end_time: int
    processing_time: int

@dataclass(frozen=True)
class ScheduleEvaluation:  # 一次解码的完整结果
    permutation: tuple[int, ...]              # 工件排列
    makespan: int
    completion_times: tuple[int, ...]         # 每个工件的完工时间
    machine_assignments: tuple[tuple[int, ...], ...]  # [工件][阶段] = 机器号
    operations: tuple[Operation, ...]
```

> `machine_assignments` 是**档案库结构距离的基础**：它记录了每个工件在每个阶段被分到哪台机器，正是「调度」区别于「排列」的那部分信息。

**核心方法：解码器 `decode_and_evaluate`**

```python
def decode_and_evaluate(self, permutation):
    permutation_key = self._validate_permutation(permutation)
    cached = self._evaluation_cache.get(permutation_key)   # ① 结果缓存，同一排列只算一次
    if cached is not None:
        return cached

    machine_ready_times = [[0]*m for m in self.machines_per_stage]  # ② 每台机器的可用时刻
    completion_times = [0] * self.n_jobs                            # ③ 每个工件的可用时刻
    ...
    for stage_id in range(self.n_stages):          # ④ 逐阶段推进（阶段间是硬约束）
        for job_id in permutation_key:             # ⑤ 阶段内按排列顺序派工
            job_release_time = completion_times[job_id]
            for machine_id in range(self.machines_per_stage[stage_id]):
                start_time = max(job_release_time, machine_ready_times[stage_id][machine_id])
                finish_time = start_time + processing_time
                if finish_time < best_finish:      # ⑥ ECT：选最早完工的机器
                    ...
            machine_ready_times[stage_id][best_machine] = best_finish
            stage_completion_times[job_id] = best_finish
            machine_assignments[job_id][stage_id] = best_machine
    return ScheduleEvaluation(...)
```

三个必须记住的性质（后面所有算法都依赖它）：

1. **确定性**：同一个排列永远得到同一个调度。
2. **阶段内保序**：因为阶段内按排列顺序派工，同一台机器上的工件必然保持排列中的相对顺序 —— 这正是 `schedule_distance` 能直接从「排列 + 机器分配」重建签名、而不用重新解码的原因。
3. **多对一**：多个排列可以映射到同一个调度（结构等价类），这是整个多模态档案库语义的出发点。

**基线启发式**

```python
def _best_insertion_order(self, job_order):
    current = []
    for job_id in job_order:                       # 按给定顺序逐个插入
        for position in range(len(current)+1):     # 穷举所有插入位置
            candidate = current[:position] + [job_id] + current[position:]
            makespan = self.evaluate(candidate)    # 取插入后 makespan 最小的位置
    return self.decode_and_evaluate(current)

def neh_heuristic(self):
    # NEH：按「各阶段平均加工时间之和」降序排列，再逐个最优插入
    job_order = sorted(range(self.n_jobs), key=self._job_average_processing_time, reverse=True)
    return self._best_insertion_order(job_order)

def spt_heuristic(self):
    # SPT：按同样指标升序（短作业优先），直接解码，不做插入
    return self.decode_and_evaluate(sorted(range(self.n_jobs), key=self._job_average_processing_time))
```

`generate_initial_solution(method, rng)` 是给 PSO 建群用的统一入口，支持 `neh` / `spt` / `random`。

### 4.2 `schedule_distance.py` — 商集签名与结构距离

**职责**：定义「两个解是不是同一个调度」以及「两个调度差多远」。这是档案库全部语义的地基。

**签名：把排列映到调度**

```python
def schedule_signature(permutation, machine_assignments):
    """返回 { (阶段, 机器): 按加工顺序排列的工件表 }"""
    buckets = {}
    for job in permutation:                # 按排列顺序遍历
        for stage in range(n_stages):
            machine = machine_assignments[job][stage]
            buckets.setdefault((stage, machine), []).append(job)   # 同一机器上自然保序
    return tuple(sorted((key, tuple(jobs)) for key, jobs in buckets.items()))
```

- **签名相同 ⟺ 是同一个调度**，可以直接用 `==` 判等价类。
- 不需要重新解码，成本 O(n·s)，可以放心在热路径里调用。

**距离：两个正交分量**

```python
class ScheduleDistance:
    @staticmethod
    def assignment_distance(perm_a, assign_a, perm_b, assign_b):
        """机器分配差异：分配到不同机器的 (工件, 阶段) 对占比，∈[0,1]"""
        different = 0
        for job in perm_a:
            for stage in range(n_stages):
                if assign_a[job][stage] != assign_b[job][stage]:
                    different += 1
        return different / (len(perm_a) * n_stages)

    @staticmethod
    def sequence_distance(perm_a, assign_a, perm_b, assign_b):
        """加工顺序差异：可比工件对中先后顺序翻转的比例（Kendall tau 型），∈[0,1]"""
        position_b = {job: i for i, job in enumerate(perm_b)}
        for stage in range(n_stages):
            groups = {}                     # 只收「两解在同一阶段分到同一台机器」的工件
            for job in perm_a:
                machine = assign_a[job][stage]
                if assign_b[job][stage] == machine:
                    groups.setdefault(machine, []).append(job)
            for jobs in groups.values():
                for i, j in combinations(jobs, 2):
                    comparable += 1
                    if position_b[jobs[i]] > position_b[jobs[j]]:
                        discordant += 1         # 先后顺序翻转了
        return discordant / comparable          # 没有可比对时返回 0
```

**为什么不用位置海明距离**（这是写论文时要讲清的一点）：

| 情形 | 位置海明距离 | 结构距离 |
|---|---|---|
| 两个解只在相邻位置交换，调度几乎没变 | 距离 1，看起来「差一点」 | 分配 0 / 顺序接近 0，正确识别为几乎相同 |
| 结构差异极大但恰好对齐了几个位置 | 距离小，看起来「很像」 | 两个分量都大，正确识别为很不同 |

**批量（向量化）距离 —— 性能关键**

标量版本本身不算慢，真正的问题在**调用次数**：「某个解 vs 档案库全部成员」是
O(m) 次，「成员两两之间」是 O(m²) 次。两层相乘，一个算例就能被拖到几十分钟。
实测 `j10c10a5` 单例卡死 20 分钟，其中 68% 的时间花在
`_pick_explore_seed → _crowding` 的 O(m²) 标量调用上。

因此 `schedule_distance.py` 另外提供一套**数值等价**的批量实现：

```python
@dataclass(frozen=True)
class ScheduleFeatures:
    # 调度的紧凑表示，供批量距离使用
    machines:  np.ndarray   # (n_jobs, n_stages) 各工件各阶段所在机器号
    pair_key:  np.ndarray   # (P, n_stages) 工件对同机器则为该机器号，否则 -1
    pair_sign: np.ndarray   # (P, n_stages) 工件对在排列中的先后（+1 / -1）

def build_features(permutation, machine_assignments) -> ScheduleFeatures: ...
def bulk_distance(features, machine_stack, key_stack, sign_stack):   # 一个 vs 一批
    # 返回 (机器分配距离数组, 加工顺序距离数组)
def pairwise_matrices(features_list, block=32):                      # 两两之间的距离矩阵
def crowding_vector(features_list):                                  # 每个成员的孤立度
```

关键是把「顺序差异」也写成可广播的形式：对每个工件对 `(a, b)` 记
`pair_key`＝两者同机器时的机器号，`pair_sign`＝两者在排列中的先后。于是

```
可比对  <=>  pair_key_A == pair_key_B != -1
翻转    <=>  可比对 且 pair_sign_A != pair_sign_B
```

与标量定义的 `discordant / comparable` 完全一致，但一次可以算一整批。

> **等价性有测试兜底**：`test_schedule_distance_bulk.py` 在随机算例与真实 Carlier
> 算例上逐对比对标量与批量结果，要求误差为 0（不是「接近」）。改距离公式时先跑它。

向量化带来的耗时变化（Small_Size 前 10 例，`--guided-rounds 60`）：

| | 优化前 | 优化后 |
|---|---|---|
| 10 例总耗时 | 95.9 s | 64.3 s |
| `j10c10a1` 引导阶段 | 65.2 s | 14.5 s |
| `j10c10a5`（原先跑不出来） | > 20 min 未出结果 | 16.1 s |

且所有语义字段（最优值 / 等优解个数 / 存档条数）逐行比对**零差异**。

### 4.3 `iterated_greedy.py`（122 行）— IG 破坏重建

**职责**：从一个排列出发做深度局部搜索。三件套：破坏 → 重建 → 退火接受。

```python
@dataclass
class IteratedGreedy:
    destruction_ratio: float = 0.3        # 每次移除 30% 的工件
    max_iterations: int = 15
    cooling_rate: float = 0.95

    def _destruction(self, permutation, rng):
        """随机挑 d = round(0.3n) 个位置，把工件取出来，剩下的保持相对顺序"""
        destroy_count = max(1, int(round(len(permutation) * self.destruction_ratio)))
        selected_indices = sorted(rng.sample(range(len(permutation)), destroy_count))
        destroyed_jobs = [permutation[i] for i in selected_indices]
        remaining_jobs = [j for i, j in enumerate(permutation) if i not in set(selected_indices)]
        return destroyed_jobs, remaining_jobs

    def _reconstruction(self, remaining_jobs, destroyed_jobs, env):
        """把被移除的工件打乱后，逐个做「贪心最优插入」放回"""
        current = list(remaining_jobs)
        for job_id in destroyed_jobs:
            for position in range(len(current)+1):     # 穷举插入位置
                candidate = current[:position] + [job_id] + current[position:]
                makespan = env.evaluate(candidate)     # 取最优
            current = best_permutation
        return current

    def _accept(self, current_makespan, candidate_makespan, temperature, rng):
        if candidate_makespan <= current_makespan:
            return True                                # 更好：必接受
        if self.acceptance_criterion == "non_deteriorating":
            return False                               # 非退化模式：只收更好的
        delta = candidate_makespan - current_makespan
        return math.exp(-delta / max(temperature, 1e-6)) > rng.random()   # SA：以概率接受劣解

    def optimize(self, initial_permutation, env, seed=None):
        """主循环：破坏 → 重建 → 评价 → 接受 → 降温"""
        temperature = max(1.0, current.makespan * 0.1)   # 初始温度按当前解规模自适应
        for _ in range(self.max_iterations):
            candidate = ...
            if self._accept(current.makespan, candidate.makespan, temperature, rng):
                current = candidate
            if candidate.makespan < best.makespan:
                best = candidate
            temperature *= self.cooling_rate             # 降温
    
    def find_multimodal_solutions(self, initial_permutation, env, n_solutions=5, seed=None):
        """多模态采样：对起点做若干次随机扰动，各自跑一遍 IG，去重后取前 n 条"""
        for _ in range(max(n_solutions * 3, 6)):
            perturbed = 随机交换 base_permutation 的若干位置
            optimized = self.optimize(perturbed, env, seed=...)
            solutions[optimized.permutation] = optimized   # 用 dict 按排列去重
```

> **注意**：`_accept` 只按 makespan 判断，不看结构。这是设计上的已知张力 —— 档案库负责「在哪挖」，但「挖到什么算好」仍然只看 makespan。想同时优化解集规模，需要把结构距离并入接受准则（`archive_guided_search._walk` 里做了一半）。

### 4.4 `niching_mechanism.py`（88 行）— 小生境与多样性

**职责**：给 PSO 提供「局部最优」的划分依据，并提供种群多样性度量。

```python
@dataclass
class NichingMechanism:
    k_neighbors: int            # 环形邻域半径
    distance_threshold: int     # 聚成一个小生境的排列距离上限

    def build_ring_neighbors(self, population_size):
        """环形拓扑：粒子只和自己的左右 k 个邻居竞争"""
        for index in range(population_size):
            ring = [(index + offset) % population_size
                    for offset in range(-self.k_neighbors, self.k_neighbors + 1)]

    def cluster_positions(self, positions):
        """小生境聚类：与某个小生境种子距离 ≤ 阈值就并入，否则开一个小生境"""
        for particle_index, position in enumerate(positions):
            for existing_niche_id, seed in seeds.items():
                if DistanceCalculator.permutation_distance(position, seed) <= self.distance_threshold:
                    niche_id = existing_niche_id; break
            if niche_id is None:                        # 谁都不像 → 自己当一个新小生境的种子
                niche_id = len(niches); seeds[niche_id] = tuple(position)
```

`DistanceCalculator` 保存的是**位置海明距离**（逐位比较）与机器分配距离，属于旧口径，现在只在两个地方还用：PSO 的小生境聚类（`cluster_positions`）和 `MultimodalArchive.summary()` 的兼容输出。**档案库的新颖性判定已全部改用 `ScheduleDistance`**。

`DiversityMaintainer.mutation_probability(diversity, stagnation_level)` 把多样性映射成变异概率：

```python
base = 0.08
diversity_boost = max(0.0, 0.25 - diversity) * 0.8   # 种群越挤，变异越猛
stagnation_boost = min(0.2, stagnation_level * 0.02) # 停滞越久，变异越猛
return min(0.45, base + diversity_boost + stagnation_boost)
```

### 4.5 `niching_pso.py`（393 行）— 离散 PSO

**职责**：用交换序做速度的离散粒子群，带小生境、自适应权重、停滞重启、档案库注入。

**粒子结构**

```python
@dataclass
class Particle:
    position: list[int]                        # 当前排列
    velocity: list[tuple[int, int]] = []       # 交换序：一串 (i, j) 交换操作
    personal_best_position: list[int] = []
    evaluation / personal_best_evaluation: ScheduleEvaluation | None

    @classmethod
    def from_evaluation(cls, evaluation):
        """从一个已评价的调度直接构造粒子（pbest 初始化 = 自身）"""
```

**速度更新（离散 PSO 的核心）**

```python
def update_velocity_adaptive(self, current_position, current_velocity,
                             personal_best, local_best, weight):
    # ① 惯性部分：旧速度里的每个交换，以概率 w 保留（w 线性递减，后期收敛）
    for swap in current_velocity:
        if self.rng.random() < weight:
            velocity.append(swap)
    # ② 认知部分：把「当前位置 → pbest」的差异表示成交换序，按比例采样
    cognitive_swaps = self._compute_swap_sequence(current_position, personal_best)
    velocity.extend(self._sample_swaps(cognitive_swaps, self.c1))
    # ③ 社会部分：把「当前位置 → 局部 gbest」的差异表示成交换序，按比例采样
    social_swaps = self._compute_swap_sequence(current_position, local_best)
    velocity.extend(self._sample_swaps(social_swaps, self.c2))
    # ④ 去重、丢弃无效交换（i == j）、截断到排列长度
    return deduplicated[: len(current_position)]
```

`_compute_swap_sequence(source, target)` 是离散 PSO 的关键技巧：把目标排列逐位对齐，需要换位时记录一个交换对，返回把 source 变成 target 的**交换序列**。这样「连续空间的速度」就映射成了「排列上的交换操作」。

**位置更新与变异**

```python
def _apply_velocity(self, position, velocity):
    candidate = list(position)
    for left, right in velocity:
        candidate[left], candidate[right] = candidate[right], candidate[left]   # 依次施加交换
    return candidate

def _mutate(self, permutation, strength=1):

        left, right = self.rng.sample(range(len(candidate)), 2)
        candidate[left], candidate[right] = candidate[right], candidate[left]
```

**入档主流程**（`add_solution`，四步严格按序）：

```python
def add_solution(self, permutation, makespan, machine_assignments) -> bool:
    self.stats["offered"] += 1

    # ① 质量门限 ρ：超出 (1+ρ)·best 直接拒收
    if self.solutions and candidate_makespan > self.quality_cutoff() + 1e-9:
        self.stats["rejected_quality"] += 1
        return False

    signature = schedule_signature(candidate_permutation, candidate_assignments)

    # ② 结构等价类去重：同一调度只保留 makespan 最优的代表元
    for index, item in enumerate(self.solutions):
        if item["signature"] != signature:
            continue
        if candidate_makespan < item["makespan"]:
            self.solutions[index] = self._make_entry(...)   # 同调度、更优 → 替换
            self.stats["replaced_in_class"] += 1
            return True
        self.stats["rejected_same_class"] += 1
        return False

    # ③ 析取式新颖性判定：只有「三个维度同时接近」才判为重复
    for item in self._quality_window(candidate_makespan):     # 二分剪枝，只比质量相近的
        machine_distance, sequence_distance = self._distance_to_candidate(item, ...)
        if (machine_distance <= self.machine_distance_threshold
                and sequence_distance <= self.sequence_distance_threshold):
            self.stats["rejected_too_close"] += 1
            return False

    # ④ 接纳，并做质量剪枝 + 容量裁剪
    self.solutions.append(self._make_entry(...))
    self.solutions.sort(key=lambda entry: entry["makespan"])
    self.stats["admitted"] += 1
    self._prune_by_quality()                    # 最优值可能变好 → 剪掉超出门限的旧解
    if len(self.solutions) > self.capacity:
        self._trim_to_capacity()
    return True
```

**为什么 `_quality_window` 很重要**：新颖性判定本身要算结构距离，如果对全库每个解都算，成本是 `O(库大小 × n²)`。但「重复」的定义里本来就含「质量接近」，所以可以先用 makespan 二分出候选窗口，只跟窗口内的解比 —— 语义完全不变，速度快一个数量级。

```python
def _quality_window(self, makespan):
    values = [item["makespan"] for item in self.solutions]     # 已按 makespan 升序
    low  = bisect_left(values,  makespan / (1.0 + rho) - 1e-9)
    high = bisect_right(values, makespan * (1.0 + rho) + 1e-9)
    return [item for item in self.solutions[low:high]
            if abs(item["makespan"] - makespan) / max(1, item["makespan"]) <= rho + 1e-12]
```

**质量剪枝与容量裁剪**

```python
def _prune_by_quality(self):
    """最优值改进后，剪掉超出 ρ 门限的旧解，保证库的语义始终成立"""
    cutoff = self.quality_cutoff() + 1e-9
    kept = [item for item in self.solutions if item["makespan"] <= cutoff]

def _trim_to_capacity(self):
    """保留最优解，其余按「最远点优先」逐个挑选 → 最大化结构分散度"""
    kept = [self.solutions[0]]                 # 最优解必定保留
    pool = list(self.solutions[1:])
    while pool and len(kept) < self.capacity:
        best_index = argmax over pool of (到 kept 的最小结构距离总和)
        kept.append(pool.pop(best_index))
```

> 对比：如果按 makespan 简单截断前 200 条，会保留一大堆几乎相同的解、丢掉结构不同的解。最远点选择保证留下的子集在结构上尽量分散。

```python
        for job_id in permutation:                     # 注意：用的是方案的固定顺序
            machine_id = machine_assignments[job_id][stage_id]     # 用的是方案的固定分配
            start = max(completion[job_id], machine_ready[stage_id][machine_id])
            if stage_id == repair_stage and machine_id == repair_machine and start < repair_time:
                start = repair_time                   # 受影响的工序顺延到修复之后
            finish = start + env.processing_times[job_id][stage_id][machine_id]
    return max(completion)

def fault_robustness(env, solutions, downtime=None):
    """对同一个停机情景，逐条重放解集，看恶化幅度与切换收益"""
    return {
        "best_after_fault": ...,          # 故障后最好的 makespan = 切到这条即可用
        "mean_after_fault": ..., "worst_after_fault": ...,
        "mean_relative_worsening": ...,   # 平均相对恶化率
        "switch_gain_vs_worst": ...,      # 相对最差方案能挽回多少
        "switch_gain_vs_mean": ...,       # 相对平均方案能挽回多少

```

> 这里刻意**不允许重新分配机器**：模拟的是「方案已经下发到车间、机器突然坏了」的场景，此时能做的只是从解集里换一条，而不是重算。这正是多模态解集相对单解算法的结构性优势。

## 7. 扩展指南：常见改动点

| 想做什么 | 改哪里 | 怎么做 |
|---|---|---|
| 换目标函数（加能耗、交期） | `hfsp_environment.decode_and_evaluate` + `ScheduleEvaluation` | 加字段并同步改 `solver_analysis` |
| 换距离度量 | `schedule_distance.ScheduleDistance` | 保持归一化到 [0,1]，否则阈值要重标定 |
| 改入档规则 | `MultimodalArchive.add_solution` | 四步顺序有依赖，别把质量门限放到等价类去重之后 |
| 把多样性写进 IG 接受准则 | `iterated_greedy._accept` | 传入结构距离，改成 `Δ ≤ 0 or (不同等价类 and 更远)` |
| 加新的种子选择策略 | `archive_guided_search._pick_*_seed` | 返回一个档案库条目即可 |
| 加新指标 | `multimodal_evaluation.evaluate_solution_set` | 追加键值，CSV 会自动多一列 |
| 加新入口脚本 | 参考 `run_carlier_multimodal_benchmark.py` | 复用 `solve_environment` + `evaluate_solution_set` |
| 换算例格式 | 参考 `load_carlier_txt` | 产出 `HFSPEnvironment` 即可，其余不用动 |

**改代码时的三条纪律**：

1. **不要绕过解码器**。任何地方需要 makespan，都必须走 `env.decode_and_evaluate`，否则结果缓存和「确定性」假设都会失效。
2. **新功能默认关闭**。像 `archive_guided_rounds = 0` 那样留开关，否则消融实验做不了。
3. **等价类判定只能用签名**，不要用排列相等 —— 排列相等是充分不必要条件，会漏掉大量真正的重复调度。

## 8. 已知限制

- **`iterated_greedy._accept` 只看 makespan**，不看结构。这是「档案库负责选在哪挖、但挖到什么只按质量判断」的根源，也是后续最值得改的一处。
- **PSO 的小生境聚类仍用位置海明距离**（`niching_mechanism.cluster_positions`），与档案库的新口径不统一。
- **档案库容量裁剪是最远点贪心**，不是全局最优的多样性子集选择，也没有理论上界；
  实现上已向量化，语义与逐对标量版逐条等价（`test_archive_capacity.py`）。
- **距离计算已全面向量化**，但只在 `n_jobs` 相同的解之间批量比较；换算例要重建特征。
- **故障鲁棒性假设「方案冻结执行」**，不允许重新分配机器，也不允许右移之外的恢复策略。
- **`_evaluation_cache` 无上限**，长跑大规模算例会持续占用内存。
